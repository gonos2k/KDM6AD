# PII 보폭 판정과 다음 계측의 영수증 연결

이 묶음은 #588에서 재현된 **진단용 큰 보폭의 교차가 두 작은 안정 보폭의 국소 판정을 가리는 P2**를 수정하고, 다음 native `(203,149)` 열 계측의 실행 영수증을 검토할 **소스 전용** 검사기를 준비한다. 새 DSO를 빌드하거나 KDM·WRF·RTTOV를 실행한 결과는 아니다. 고정 [45개 입력 계획](../harness/evidence/native_host_preflight_2026-11-12/README.md)의 SHA-256 `4d6a935c9d83d987a8a2149d58699b2812af565785d20c599cf9f49f05846b8a`와 100회·900초 상한은 유지한다.

## 교차 보폭의 역할 수정

판정기는 관측값을 보기 전에 같은 중심·방향에서 **가장 작은 서로 다른 두 계획 보폭**을 국소 판정용으로 선택한다. 큰 나머지 보폭은 진단용이다. 각 보폭의 입력·출력·기록된 마스크와 결과 태그는 모두 검사하고 보존한다. 전체 수치 태그는 선택된 두 보폭의 교차·퇴화·불일치·미해상·반올림 제한을 집계한다. 진단용 교차만으로는 선택된 두 보폭의 일치를 가리지 않는다.

상측 PII의 고정 계획에서는 `h=10⁻⁶`·`10⁻⁵`가 선택되고 `10⁻⁴`는 진단용이다. 고정 계획의 **합성 선형 출력**으로 두 작은 보폭이 `STEP_NUMERIC_CONSISTENT`, 큰 보폭이 `BRANCH_CROSSING`일 때 전체 수치 태그가 `LOCAL_NUMERIC_CONSISTENT`가 되는 것을 검사했다. 선택된 한 보폭의 JVP를 바꾸면 `NUMERIC_MISMATCH`, 0으로 바꾸면 `UNRESOLVED`가 된다. 이는 #586/#587의 실제 PII 미분 합격이 아니다. 모든 결과에서 출처 상태와 `NOT_ELIGIBLE` 차단은 유지된다. [수정된 기준](NATIVE_HOST_OUTPUT_FD_GATE_V1_20261112.md)

#588의 45개 입력 `plan.json.gz`는 바꾸지 않았다. **보폭 선택 정책은 이번 후속 코드·문서 버전**으로 따로 고정하고, 미래 실행은 계획 해시와 이 정책을 포함한 Git 커밋을 함께 인용해야 한다. 이후 보폭 역할이나 소스가 바뀌면 기존 계획·정책을 덮어쓰지 않고 새 버전으로 기록한다.

## 같은 호출의 바이트·기록 연결

`receipt_schema.py`는 미래 제출자가 제공할 완전한 자료 묶음의 **내부 계약**을 검사한다.

| 대상 | 소스 전용 검사 |
| --- | --- |
| 호출 목록 | 계획된 100개를 순서·입력·mode별로 대조. 필수 93개는 성공, 선택 7개는 성공 또는 구체적 skip 이유. 각 완료 호출의 출력 파일 SHA·입력 624단어·출력 468단어를 대조 |
| 값 비침습성 | 같은 입력의 capture off/on 468단어를 정확히 비교하고 중심 graph·실행한 설치본 값 호출과도 대조 |
| 출처 주장 | 계획·소스·새 DSO·설치 DSO·컴파일 플래그·assertion·Torch 의존성 해시와 새 계측 소스 자산의 **제출된 바이트**를 대조 |
| 미분 seed | 네 명목 방향의 624단어 one-hot JVP seed와 명명한 468단어 VJP cotangent를 재구성해 live 기록에 연결. 별도로 **21개 중심·방향·보폭의 실제 표현 seed**와 JVP 출력 468단어·해시·중심 graph 호출/handle·반환 코드를 대조 |
| 필드 inventory | 일곱 그룹의 명시된 요구 항목마다 각 값 입력의 value/mask 기록과 중심의 해당 JVP/VJP 기록을 검사. 비활성 값은 **같은 호출·층·substep·stage·항목의 거짓 마스크**와 구체적 사유가 필요하며, 비활성 마스크·graph 접선은 현재 허용하지 않음 |
| 실행기 연결 | 별도 예산 영수증의 계획·DSO·제어값, 100개 호출 ID·상태, 출력 경로·SHA와 제출 자료를 비교 |

이 검사는 **제출자가 붙인 항목명과 자체 자료의 일치**를 확인할 뿐, 그 이름이 실제 물리식의 올바른 텐서인지, DSO가 해당 소스에서 빌드됐는지, 로더가 그 바이너리를 사용했는지를 독립 인증하지 않는다. 효과적인 21개 seed와 **최종 출력 JVP의 바이트 연결**은 있지만 중간 과정의 effective 접선과 모든 분기 기록이 연결된 것은 아니어서 `fd_gate_ready=false`다. 따라서 영수증 검사를 통과해도 `NOT_ELIGIBLE_UNVERIFIED_PROVENANCE`다. 실제 실행의 필수 필드 전체 존재와 inactive 사유를 인증하려면 계측 소스·실행 경로와 별도의 검토가 더 필요하다.

## 예산 실행 어댑터의 차단 범위

`execute_budget.py`는 **SHA로 고정한 저장소 테스트 스텁의 다섯 시나리오만** 합성 시험 모드에서 실행한다. 기본 경로는 현재 `SPEC_ONLY` 계획의 DSO 해시를 채워도 실행 전에 거부한다. 합성 모드는 임의 실행 파일·`-c` 코드·추가 환경변수를 거부하고, 격리 Python `-I -S` 및 고정 세 thread 변수 아래에서 계획·source·DSO·dependency 바이트를 호출 전에 확인한다. 스텁 호출·출력 기록·자산 해시까지 단조시간 상한에 포함한다. 종료 신호·timeout에서 프로세스 그룹을 정리하고 남은 프로세스 또는 권한 오류를 실패로 보고하며, 완료·건너뜀·실패·미시작 호출을 모두 남긴다. 파일 동기화나 OS 스케줄링 때문에 900초를 약간 넘을 수는 있지만 이를 `INCOMPLETE`로 기록한다.

현재 모듈은 **실제 C ABI 생산자가 아니다.** 새 계측 DSO를 가진 별도 `EXECUTION_READY` 후속 계획과 실제 로더·호출·출력 영수증이 등록되기 전에는 45개 입력을 실행하지 않는다. #588의 `SPEC_ONLY` 파일을 덮어써 실행 근거로 바꾸지 않고, 후속 계획과 게이트 코드 버전을 구분해 고정해야 한다.

## 검증 범위와 다음 작업

일반·최적화 모드에서 P2의 세 보폭 조합과 영수증/seed/필드/timeout 변조 시험을 수행한다. 공개 CI는 **합성 자료와 저장 증거를 검사**하며 비공개 archive·DSO를 재빌드하지 않는다. 다음 물리 실행 전에는 실제 계측 소스의 `-ffp-contract=off`, assertion, on/off 전체 출력 원시 비트 일치와 graph 텐서의 수명을 확인하고, 종별 적용 침강·총강수·열·BG의 실제 피연산자를 한 빌드에 넣어야 한다. 물리 단위·과정 수지·전체 호스트 AD·GK2A–RTTOV 비용 미분은 남아 있으며 `scientific_status`와 `physical_unit_status`는 계속 `INCONCLUSIVE`다.
