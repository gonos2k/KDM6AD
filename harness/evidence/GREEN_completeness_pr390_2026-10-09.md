## Independent RTTOV verification

The worktree graph query was run before this audit’s file writes. It returned MPI/control nodes but no private RTTOV source/build path; the private path therefore needed direct source and receipt checks.

The modified `rttov_eddington_setup.F90` is a copy-on-write diagnostic source. Comparing its 506 Fortran source units against the installed source found one changed file, `main/rttov_eddington_setup.F90`. A line diff contains four insertion-only blocks (27 lines total), with no original lines deleted or replaced. The added writes surround the source’s `ANY(ext > 20)` flag and `MIN(ext,20)` clip. The source hashes match the build receipt. Of 507 object files, only `rttov_eddington_setup.o` differs; of 20 static libraries, only the two main archives were re-archived. The recorded gfortran compile and link commands match the logs and return successfully. The instrumented executable, object and archives match their recorded hashes.

The saved input tree has 22 files. Every input hash matches between `case_00`, the untouched-executable baseline rerun, and the instrumented rerun. The three runs also use an identical `out/rttov_test.txt` control hash. The original RTTOV executable, audited installed source, coefficient file and hydrotable hashes match the recorded identities. All 11 direct/K numerical products hash identically across the retained case, original-executable rerun, and instrumented rerun.

The raw dump has exactly 4,752 rows: two setup calls × nine channel slots × 66 layers × two hydro categories × pre/post clip. Every expected key has both phases. Recalculation from the dump confirms each postclip value equals `min(preclip, 20)` exactly and the two call arrays are identical. `channels.txt` requests IDs 8–16; `lallchans=.FALSE.` maps slots 1–9 to those IDs in order. The first direct setup call and the K call’s forward pass are supported by the test and RTTOV caller order. The profile has 67 pressure interfaces in hPa and 66 top-down layers; the measured layer 64–66 interface pairs match the report. RTTOV source defines `ltick` in km and extinction in km⁻¹; the 20 km⁻¹ limit and quality bit 15/value 32768 are source-supported.

The channel-8 crossings are layers 65–66 (maximum 38.407032752 km⁻¹); channel-9 crossings are layers 64–66 (maximum 22.595689756 km⁻¹). Channel 10 peaks at 5.987125995 km⁻¹. The source and input check show aerosol scattering disabled and hydrometeors enabled, with all 528 hydrometeor-content values and 67 fractions zero. The 462 effective-diameter parameters include 78 nonzero values. This supports zero hydrometeor mass/fraction and the measured zero increment; it does not mean every hydrometeor-related parameter file is all-zero. Category 0/1 totals match for the captured values.

One P3 measurement qualifier remains: the dump writes the local `ext_clear` *after* the source applies `MAX(scatt_aux%ext_clear, 1e-10)` ([instrumented source, line 180](../../graphify-out/pr390-local/rttov/source-copy/src/main/rttov_eddington_setup.F90), with values written at line 226). Some non-triggering rows equal that 1e-10 floor. The reported trigger-layer bases all exceed 20 km⁻¹, so this does not alter the reported threshold crossings or channel attribution. The raw dump does not preserve the unfloored clear-sky base at every layer; category equality alone should not be used to infer hidden sub-floor increments in other layers. This is a diagnostic-label/scope issue, not a production defect or a defect in the measured warning layers.

The post-run receipts therefore support a profile-specific warning attribution from the separate diagnostic build. The untouched executable independently reproduces the saved numerical outputs, but its historical source-to-binary association is not attested. The new arrays do not expose historical binary internals, individual gas species, or behavior in the seven other saved profiles.
