## Prospective numerical gate

`fd_gate.py` implements the proposed [output-wise FD gate](../../../docs/NATIVE_HOST_OUTPUT_FD_GATE_V1_20261112.md) for **future** endpoint data. Normal operation binds a requested center, direction, output index and steps to the SHA-pinned canonical `plan.json.gz`; synthetic tests use an explicit test-only mode. Before examining observations, it selects the **two smallest distinct planned steps** for local acceptance and labels all larger steps diagnostic. Each step still checks all 624 input words, the actual componentwise represented direction, 468-word forward parity supplied by the caller, finite outputs, captured-mask and schedule inventories, the 16-output-ULP resolution floor and relative FD–JVP residual. A diagnostic crossing is retained but does not override two consistent selected steps. A crossing, mismatch or unresolved signal in a selected step remains fail-closed; one selected step cannot yield a final local consistency tag.

The gate compares **caller-supplied** execution arrays and receipts. Until future independent asset hashes and executed-path provenance are checked, its result remains `UNVERIFIED_EXECUTION_RECEIPTS` and `NOT_ELIGIBLE` even when synthetic numbers satisfy the local formula. It does not assign a new pass to #586/#587 saved rows and does not prove hidden-branch stability, installed joint AD, physical budgets or RTTOV cost derivatives. `scientific_status` and `physical_unit_status` remain `INCONCLUSIVE`.

The numerical aggregation selects the **two smallest distinct planned h** before inspecting outputs. On canonical upper PII, `10⁻⁶` and `10⁻⁵` are acceptance steps and `10⁻⁴` is diagnostic. A diagnostic crossing remains in the per-step result but cannot veto two locally consistent selected steps; a crossing, mismatch, rounding-limited or unresolved **selected** step still prevents `LOCAL_NUMERIC_CONSISTENT`. The result exposes each step's role and the selected IDs. This fixes the false negative reported after #588 without changing the frozen 45-input plan or lowering the evidence eligibility bar.

## Future receipt and budget adapters

`receipt_schema.py` checks a **caller-supplied** prospective bundle against the frozen plan. It requires all 100 ordered call entries (93 required completed; seven optional completed or explicitly skipped), hashed raw call assets with the planned 624 input words, off/on and graph/installed 468-word value parity, build/source/dependency hash claims, four nominal one-hot JVP seeds and a named one-hot VJP cotangent. It separately derives **21 per-center/direction/step represented JVP seeds** from the planned endpoint words and checks each submitted seed, center graph handle/sequence, graph forward 468 words, JVP output 468 words/hash and return code. Seven-group value/mask/live-record coverage is required; an inactive value needs a false mask at the **same call, stage, layer and substep**, while inactive masks and graph tangents are unsupported. The live rows bind their nominal seed bytes and hashes to complete call/substep/level/stage/field/direction identity. A separate bridge matches these entries to the synthetic scheduling envelope by call, status, path and digest. These checks establish internal byte relationships; the submitted source labels, build claims and physics meaning are **not independently authenticated**. Per-step final-output JVP bytes are linked, but effective live intermediate tangents and independent execution provenance are not, so `fd_gate_ready=false` and the return status is always `NOT_ELIGIBLE_UNVERIFIED_PROVENANCE`.

The future receipt-to-FD adapter additionally requires **45 call-specific condition assets** with the source-pinned #586 inventory of 1,170 Boolean and 195 schedule identities. It binds those values to each capture-on sequence and constructs center/endpoint/`+2h` gate inputs without default masks. The contract covers only the previously captured identities. Nineteen new masks proposed by the source-level field contract remain `BLOCKED` and are rejected as undeclared keys until a reviewed successor is registered. The adapter still returns `fd_gate_ready=false` and `NOT_ELIGIBLE`; no real execution is certified.

`execute_budget.py` is a **synthetic-only scheduling adapter**. Its default `run()` rejects production execution even when the caller fills the `SPEC_ONLY` plan's missing DSO hash. Explicit synthetic-test mode accepts only the SHA-pinned repository stub with five fixed scenarios under isolated Python `-I -S` and an exact three-variable thread environment; arbitrary executables, `-c` code and extra environment values are rejected. The adapter pins the canonical compressed plan and submitted dependency/source bytes before each synthetic subprocess; records every requested, skipped, failed or unstarted call; includes output/asset hashing in monotonic time; and tries to terminate and verify the whole process group on timeout or signal. A separately committed `EXECUTION_READY` successor plan, actual isolated DSO, ABI producer, independent loader/execution attestation and semantic field review are still required before real capture. The adapter may report an overrun as `INCOMPLETE` if filesystem sync or OS scheduling finishes after the wall deadline; it cannot promise hard real-time termination.

The same clock now starts **before initial asset validation** and remains active through final receipt and completion-candidate `fsync`. Repeated termination signals are recorded without interrupting group cleanup. The on-disk receipt and `completion.json` are explicitly **candidates**, never sufficient for completion. A separate `synthetic_supervisor.py` forks the scheduler, observes its actual exit and full parent wall, and requires a return token written only after `scheduler.run()` returns before publishing a synthetic witness. The bridge requires witness and token bytes/hashes; a marker-only file, post-publication interruption, premature zero exit, overrun or failed corrective write cannot be accepted. These are unsigned synthetic scheduler relationships, not authorization for the actual ABI producer.

`fd_input_adapter.adapt_many()` validates one fresh receipt snapshot and its 45 condition assets once, then performs the full gate formula separately for every requested output. It does not cache across invocations or share mutable output results. A three-output synthetic comparison matched repeated `adapt()` calls (2.436 s repeated versus 0.893 s batch); one 468-output batch took 47.253 s. These are local measurements, not a measured CI speedup, and the adapter remains `NOT_ELIGIBLE` with `fd_gate_ready=false`.
