## Result

All four legs passed the current verifier's external manifest, fixture, Gate A,
source-commit, and C++ evidence-tree checks. Each Fortran A/B/C set is raw-bit
noninvasive: 7,141 legacy operations and 6,956 conservative operations were
recorded. The C++ bundle records 62 containers per algorithm and reproduces its
three-loop schedule with main-chain `mstep` 1–10.

Both the legacy and conservative pair first diverge at the same identity:
`micro_freeze_heat`, loop 2, column 3, k 0, `xlf`. The recorded freeze input
temperature and all three f64 rates match between trees. At this cell, Fortran
has `xlf=0x488740a0`, `cpm=0x447b5809`; C++ has `xlf=0x488911e0`,
`cpm=0x447b36a5`. The comparator's exact f32 counterfactual gives Fortran
`t=0x437396ba` and C++ `t=0x437396bb`; the `xlf` difference accounts for the
stored one-ULP change and `cpm` contributes zero in that counterfactual. The
verifier still lists other `xlf` consumers—melt heat and `xlwork2`—as unresolved,
so this result cannot promote a mechanism pass.

The target loop-2 `outer_post_micro.qr` difference is also captured and replayed
from the actual update operands. At column 3, k 0, all four legs have
`outer_post_sed.qr=0x3321b6c9` and
`micro_pre_state_update.qr=0x31959f04`. The cold branch agrees. The active
`prevp` and `psacr` operands differ between Fortran and C++; the checked-in
source-order `replay_qr` reproduces `micro_post_state_update.qr` and
`outer_post_micro.qr` exactly: Fortran `0x31974466`, C++ `0x31974463`, in both
algorithm pairs. The record shows a shared −3 ULP target-cell result. It does not
attribute the full historical maximum-ULP envelope or decide which coefficient
lifetime is physically preferred.
