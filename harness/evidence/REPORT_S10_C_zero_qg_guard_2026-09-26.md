## One-factor contract

C starts from the existing B midpoint source. It keeps the same per-call OUT initialization, active `ProgB_param` path, and the explicitly unapproved `rho_mid=400 kg m-3` positive-trace fallback. The only physical change is at each `rate/rhox` volume quotient: bypass only when the qg value at that exact consumer and that same process-rate numerator are both exactly binary32 zero. That arm assigns a zero quotient. Every other combination executes the original division. Thus `qg=0, rate!=0` still transfers through the original division; `qg!=0, rate=0` also takes the original division and must pass the finite-positive-density check. No qg/rate/rhox clipping or blanket process gating is introduced.

The `pgmlt/rhox` consumer is after the source updates qg and temperature. Its producer branch is entered only for positive pre-melt qg. If `pgmlt` is zero, the post-update qg remains positive; if the post-update qg is zero, `pgmlt` must be nonzero. Thus the exact-zero qg/rate guard is unreachable at stage 1 under this producer condition. The zero arm nevertheless retains the `brs = brs + 0.` store. `pgdep/rhox` follows the qg mass generation update; its zero arm retains the leading `0.` addend before `biacr` to preserve the source-ordered binary32 word behavior. `pgevp/rhox` and `pgeml/rhox` precede their qg mass update; nonzero rate values remain on the original division arm even if qg is zero at that use.

The four guarded quotient consumer IDs are 1418 (`pgmlt/rhox`), 2824 (`pgdep/rhox`), 2915 (`pgevp/rhox`), and 2916 (`pgeml/rhox`). The `piacr`, `paacw`, `pgacr`, `pgacs`, `biacr`, `braci`, `bsacr`, `bracs`, `bgaci`, `baacw`, and `bgacr` source terms and all temperature formulas remain unguarded and source-ordered.

The C-only `S10ZG` rows report call key, consumer ID, bypass/divide action, qg, rate numerator, and rhox; they do not contain a quotient field. The applied quotient snapshot is recorded in the corresponding `S10VOLUME` row. The selected columns are `(j=73,i=113/115)` for the first microphysics step; no full-domain arrays are published. `S10MASS`, `S10VOLUME`, and `S10HEAT` report the actual source operands and stores at the melt, generation/deposition, and warm-evaporation stages. Replay requires the fixed call×column×level gate census plus caller-supplied stage-1 keys and event-log SHA-256. The replay API checks those inputs against the rows, but no independent native run-receipt binding currently authenticates either supplied value. It checks the exact-zero action predicate; it verifies every action-0 rate and quotient are zero, every action-1 divisor is finite and positive, and every nonzero rate remains on action 1. It then recomputes qg mass, brs volume, and temperature stores using binary32 word equality in source order, including distinguishing positive and negative zero. The native discovery key set, receipt binding, and log digest do not yet exist; therefore native replay acceptance remains OPEN.

Before any host run, synthetic tests cover `qg=0/rate=0/rhox=0`, qg zero with nonzero rate, positive qg with zero rate, invalid action mutations, non-density brs terms, latent-rate terms, and binary32/signed-zero ordering.
