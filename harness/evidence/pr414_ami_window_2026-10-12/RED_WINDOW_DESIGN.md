# Red design review: Jul19 three-observation held-forcing window

## Design assessment

The proposed core design is mathematically coherent as one dual minimization from the retained Jul19 initial native background, with one T/Q state prior and three observation costs evaluated along one 61-step KDM trajectory. The observations at integer indices 1, 31, and 61 correspond to model slots 05:56, 06:06, and 06:16 under the declared 20-second clock from 05:55:40. The fixed initial forcing `f0` repeated for all 61 steps is an explicit zero-order-held-forcing hypothesis; this is a forecast-backed local KDM window, not a replay of saved WRF states through 06:16, host forecast cycling, or evidence of exact pixel UTC.

The existing `run_da_window` and `run_dual_minimizer` APIs can express this without changing the solver. `run_da_window` has one `State x0`, a sequence of transition forcings, and an observation callback indexed at `x_t` before transition `t` (including terminal `x_T`). `make_dual_frozen_obs_eval` supports a `y_by_time` mapping and freezes a separate background-quality mask/signature for each observation slot. The V4 single-observation capture wrapper is not used unchanged for this multi-time case; the new runner must retain equivalent provenance and audit evidence for all three slots.

## Red checks for the runner

- Keep the original PR412 native initial state at `2025-07-19_05:55:40`, the same selected column, and all 61 transition forcings exactly equal to the pinned `f0`. The slots are 1, 31, and 61, so the times follow directly from the declared 20-second step. Preserve the saved forcing's center pressure and corresponding native P8W interface pressure exactly. With the forcing held constant, the H grid and frozen optical dry-air density remain the original background/f0 values at all slots; do not update density from trial qv or claim later host pressure/state snapshots were consumed.
- Bind three independent seven-channel BT/DQF inputs and their source/scene/nominal-slot metadata. Compute each slot's own background RTTOV quality, frozen mask, valid count and signature. Preserve the distinction between reader DQF and model `rad_quality`; require the declared support rule at each slot, and fail if any frozen-support channel becomes quality-invalid during a trial. Do not reuse the 05:56 BT, mask, or observation identity at 06:06/06:16.
- The time-keyed observer should return the three per-slot Huber costs and their state covectors into a single `ObsEvalResult` path for the unchanged dual minimizer. The total objective is one initial-state prior plus the sum of the three per-slot observation costs; do not apply three separate initial priors or run three minimizers under a joint-window label. Keep the same zero-start T/Q control sigmas and fixed inactive microphysics parameters.
- The final audit should separately bind returned BT, DQF, model quality, mask/signature, valid count, time index, and H configuration for all three slots. Record optimizer iterations/evaluations, termination as exposed, full 61-step state-control gradient, and the one-shot execution identity. Count H work as logical slot callbacks unless internal RTTOV/K process launches are actually instrumented.
- `run_da_window` does 61 forward KDM steps and recomputes 61 local graphs for the backward VJP in each objective evaluation. L-BFGS line-search closures repeat this work, and the time-keyed observer calls three H slots per closure. Checkpoints are value-only states; this is compute-heavy but still the existing one-column/window solver, not a new algorithm. Report actual counts and return status without inferring that all 61 steps equal a saved host forecast or that unknown termination means convergence.

## Scope limits

The later observations are mapped from nominal AMI slot labels; unless per-pixel UTC is verified, retain that assumption and do not state exact pixel-time collocation. The only host state used as `x0` is the retained 05:55:40 column. Forcing `f0` held through 61 local steps makes the operator's pressure and geometry internally consistent with the fixed-forcing experiment, while leaving the later host forecast states unused as truth. Any later-state comparison is a separate diagnostic and must not silently restart or re-prior the joint analysis.

This assessment covers the declared design, not an executed run. I made no data/model/M/H/optimizer calls and did not edit the runner. Before an actual run, the preflight still needs to bind the three real observation payloads, native input/checkpoint, fixed f0 sequence, time-keyed H configs, source hashes, and fresh output paths.
